# 우선순위 결정 근거

## 왜 이 분류인가

세 보고서는 각각 다른 렌즈로 같은 제품을 본다. 보안은 기술 리스크를, 시장 분석은 진출 가능성을, 운영 플레이북은 1인 체제의 지속가능성을 본다. 세 가지가 겹치는 지점은 **"지금 상태로 공개하면 누구에게 어떤 피해가 갈 수 있는가"**다.

## P0 — 11개

**기준**: 하나라도 남아 있으면 보호자 5명 이상 공개 시 개인정보보호법 제64조의2(매출 3% 과징금) 리스크.

- 전부 `area:security`. 시장·운영 항목은 P0이 없다.
- 이유: 제품 기능은 완성되었고 법적·규제 리스크만이 "오늘의 차단 요인"이기 때문.
- 보안 보고서의 Critical 3 + High 7 + Medium 중 즉시 조치 가능 1건으로 구성.

## P1 — 28개

**기준**: Closed Beta 5개 시설 운영을 안전하게 하려면 필요.

- `legal(5)`: 베타 시설과 법적 계약 없이 시작하면 시설도 수탁자 의무 위반.
- `product(3)`: CSV import, 대시보드 — 없으면 온보딩 2시간이 10시간이 됨.
- `ops(7)`: 혼자 운영하는 SaaS는 **모니터링·백업·런북 셋 없이 1주도 못 버틴다.**
- `security(6)`: Critical 해소 후 바로 따라오는 공격 벡터들.
- `biz(7)`: 부모님 시설 1곳을 넘어 5곳으로 확장하려면 레퍼런스 영상·콜드 아웃리치·시범사업 1건 필요.

## P2 — 28개

**기준**: Paid Beta → GA 전환. MRR 200만원을 만들려면 결제·지표·가격이 결정되어야 함.

- `security(8)`: Medium 취약점 + Low 일부. Deep defense 레이어.
- `ops(7)`: Alembic·OpenTelemetry·테스트 — **기술 부채를 갚아야 확장 가능**.
- `product(4)`, `biz(6)`, `legal(3)`: GA 체크리스트의 나머지.

## P3 — 18개

**기준**: 유료 10~25개 시설 + MRR 500만원 이후의 스케일·인증·조직.

- `security(4)`: 침투테스트·SOC2 준비 수준은 고객 2~3곳 확보 후에만 의미.
- `product(5)`: 다국어·캘린더·보호자 간 메시지 등 기능 확장.
- `funding(4)`: 엔젤·TIPS·채용은 매출이 나온 뒤 옵션이 열림.
- `legal/인증(4)`: SOC 2 / ISMS-P / KMS / PIA — 대형 고객 수주용 증빙.

## 우선순위 재검토 트리거

아래 사건 발생 시 `KANBAN.md`의 우선순위를 재조정:

1. **개인정보 사고 발생 또는 근접**: 관련 P2/P3 즉시 P0로 승격
2. **유료 고객 3개 돌파**: P3 `legal/funding` → P2로 당김
3. **직원 1명 채용**: `ops` 항목 중 자동화 대체된 것 제거, `hiring` 쪽 항목 생성
4. **대형 고객 수주 협상**: 해당 고객이 요구하는 인증 즉시 P1로 승격

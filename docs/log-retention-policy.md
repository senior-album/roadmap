# 로그 보관 기간 정책

**상태**: Phase 1 (정책) + Phase 2 (DB 자동 파기 구현). Loki retention 은 T-042 PR 에서 이미 적용.
**관련 이슈**: T-182 (roadmap#67)
**갱신 주기**: 분기 1회 또는 법령 개정 시.

---

## 0. 목적

각 로그 유형에 대해 **얼마나 보관하고, 언제 파기하며, 왜 그 기간인지** 를 합의. PII 노출 최소화(개인정보보호법) 와 사고 조사(T-181 유출 대응) · 보안 감사 · 법정 최소 보관 요건 사이의 균형.

본 문서는 **정책** 만 정의. 실제 파기 스케줄러 구현은 Phase 2 (후속 이슈로 분리).

## 1. 법정/규제 최소 보관 기간 (먼저 깔아두는 하한선)

| 로그 유형                      | 법령                       | 최소 보관            |
|--------------------------------|----------------------------|----------------------|
| 웹사이트 방문 기록(접속 IP 등) | 통신비밀보호법 §15-2, 시행령 §41 | **3개월**            |
| 로그인 이력                    | 정보통신망법 §29, 시행령 §16  | **1년**              |
| 개인정보 처리 이력(제공·파기)  | 개인정보보호법 §30, 시행령 §30 | **3년**              |
| 전자상거래 거래 기록           | 전자상거래법 §6 (해당 시)     | **5년**              |

> 본 서비스는 전자상거래 대상이 아니므로 최하단 불적용. 금융/거래정보 없음.

이 하한선보다 **짧게** 설정하면 법 위반. 길게 설정할 순 있으나 PII 노출 창이 커짐.

## 2. 로그 카테고리별 정책

### 2-1. 애플리케이션 로그 (stdout / Loki)

출처: backend / photo-worker / frontend nginx / cloudflared / MinIO / Postgres / OpenSearch / Redis 파드 stdout.

| 항목                  | 값                                                   |
|-----------------------|------------------------------------------------------|
| 보관 기간             | **30일**                                              |
| 저장 위치             | (현재) `kubectl logs` — 파드 재시작 시 손실. (T-042 후) Loki |
| PII 포함 가능성       | 높음 — PIIRedactionFilter(T-103) 로 이메일/휴대폰 마스킹. 이름/주소는 개별 호출부 책임 |
| 파기 방식             | Loki compactor `retention_period: 720h` (30d)        |
| 근거                  | 감사 최소 요건 < 법정 하한(1년, 로그인 이력). 로그인 이력은 §2-3 에서 별도 90일로 분리 |

### 2-2. API access log (uvicorn access)

| 항목            | 값                                  |
|-----------------|-------------------------------------|
| 보관 기간       | **90일**                            |
| 저장 위치       | Loki (T-042 후). 현재 stdout.        |
| PII             | URL path/query 에 공유 토큰 포함 가능 → token 부분은 로그 레벨에서 마스킹 필요 (후속 이슈) |
| 파기 방식       | Loki `retention_period` 별도 라벨 기반 |
| 근거            | 통신비밀보호법 3개월 충족 + 운영 조사 여유 |

### 2-3. 인증 관련 로그 — 로그인 / 토큰 발급 / 실패

| 항목          | 값                                                     |
|---------------|--------------------------------------------------------|
| 보관 기간     | **1년**                                                |
| 저장 위치     | Loki 라벨 `category=auth` + backend `refresh_tokens` 테이블 (세션) |
| 필드          | ts, user_id, event(login/refresh/logout), ip, ua, result |
| 파기 방식     | Loki retention + refresh_tokens 테이블은 `expires_at` 기반 DELETE CronJob |
| 근거          | 정보통신망법 §29 시행령 §16 (1년 법정) 충족             |

### 2-4. 권한 · 감사 로그 (photo_audit_logs / admin_audit_logs)

| 항목          | 값                                                     |
|---------------|--------------------------------------------------------|
| 보관 기간     | **3년**                                                |
| 저장 위치     | postgres 테이블 (구조화). backup(T-043) 포함.          |
| 필드          | actor_id, target, action, at, ip / (admin 은 추가로 reason) |
| 파기 방식     | `DELETE WHERE at < now() - interval '3 years'` CronJob (Phase 2) |
| 근거          | 개인정보보호법 §30 (처리 이력 3년) + T-181 유출 조사 시 가장 중요 |

> **유출 조사 시 이게 없으면 §3-1 체크리스트 대부분을 답할 수 없음**. 3년 미만으로 단축 금지.

### 2-5. 백업 로그 (pg_dump / MinIO mirror CronJob 실행 기록)

| 항목          | 값                                              |
|---------------|-------------------------------------------------|
| 보관 기간     | **90일**                                        |
| 저장 위치     | Loki 라벨 `job=backup`                          |
| 파기 방식     | Loki retention                                   |
| 근거          | 백업 실패 추세 분석 + 재시도 정책 조정용. 3개월 이상 과거는 의미 저하 |

### 2-6. 보안 스캔 결과 (Trivy / gitleaks / pip-audit SARIF)

| 항목          | 값                                                            |
|---------------|---------------------------------------------------------------|
| 보관 기간     | **영구** (리포지토리 GitHub Security 탭)                       |
| 저장 위치     | GitHub Advanced Security / Actions artifact                    |
| 파기 방식     | 수동 (GitHub 이 자동 rotation 하지 않음)                        |
| 근거          | CVE 대응 추이 분석은 장기 축적이 필요. 개별 finding 데이터는 작음 |

### 2-7. 원본 백업 파일 (pg_dump dump, MinIO mirror)

백업 "**파일**" 은 로그 아니지만 보관 정책 일관성 위해 여기 같이 명시.

| 대상                     | 보관 기간 | 구현 위치                                         |
|--------------------------|-----------|---------------------------------------------------|
| pg_dump (R2)             | **14일**  | T-043 CronJob 의 `mc rm --older-than 14d`         |
| MinIO 미러 (R2)          | **영구**  | 사진 원본이라 삭제는 사용자 요청 시(T-180) 개별 처리 |
| 인시던트 기록 (`docs/incidents/`) | **5년**   | git history. 수동 보관.                              |

### 2-8. 운영 편의 데이터 (만료/완료된 row)

법정 보관 의무 없음 — 기능 가치가 사라진 row 를 정리하는 카테고리. 인증 토큰은 보안 관점, 그 외는 DB 폭증 방지.

| 테이블                    | 보관 기간 | 근거                                                 |
|---------------------------|-----------|------------------------------------------------------|
| `refresh_tokens` (만료된 row) | **즉시 (만료 후 0일)** | 만료된 refresh token 은 인증 가치 0. 즉시 삭제가 보안상 안전 |
| `photo_shares` (만료된 link) | **30일**  | 만료 후 단기 추적성 (누가 언제 만든 링크였는지) 만 유지 |
| `photo_processing_jobs` (completed / failed) | **60일** | 큐 추세 분석 끝난 후 가비지. failed 도 60일 안에 운영자가 retry/포기 결정 |
| `notifications`            | **90일**  | 운영 편의 — 사용자에게 도달한 후 가치 저하. 법적 의무 없음 |

## 3. 파기 방식

각 카테고리마다 파기 주체가 다름.

| 카테고리                                           | 파기 주체                                                  | 상태                              |
|----------------------------------------------------|------------------------------------------------------------|-----------------------------------|
| §2-1, §2-2, §2-5                                   | Loki compactor (`retention_period` config)                  | ✅ T-042 PR 에서 적용 (Loki 30일)  |
| §2-3 인증 이벤트 로그                              | Loki compactor (별도 라벨 retention 미적용 — 후속 이슈)      | ⏳ 후속 이슈 (라벨 기반 retention) |
| §2-3 `refresh_tokens` (만료된 row)                 | backend `app/scripts/purge_expired_logs.py` + k8s CronJob   | ✅ 본 PR (T-182 Phase 2)           |
| §2-4 `photo_audit_logs` / `admin_audit_logs` (3년) | 동일                                                       | ✅ 본 PR                           |
| §2-7 pg_dump (R2 14일)                             | T-043 CronJob `mc rm --older-than 14d`                      | ✅ T-043 적용 완료                 |
| §2-7 MinIO 영구                                    | 사용자 파기 요청 경로 (T-180)                                | ⏳ 별도 이슈 (T-180)                |
| §2-8 운영 편의 데이터                              | 동일 `purge_expired_logs.py` + CronJob                       | ✅ 본 PR                           |

본 PR 의 cron 스케줄: 매주 일요일 19:00 UTC (= 월요일 04:00 KST). pg_dump(18:00 UTC) 와 1시간 차이를 둠.

추가 파생 이슈:
- 인증 이벤트 로그 (§2-3 Loki 1년) — 라벨 기반 retention 분리 필요
- 파기 실행 자체의 감사 기록 — 본 PR 은 `purge_expired_logs` stdout (Loki 가 잡음) 로 단순화. `data_purge_logs` 테이블 신설은 보류 (over-engineering)

## 4. 예외 / 보류

### 4-1. 법적 홀드 (legal hold)
유출 사건 조사 중 / 소송 발생 시 관련 로그는 보관 기간 종료 후에도 **보관**. 구체적 상황 발생 시 수동 결정 — 정책 규칙으로 자동화하지 않음.

### 4-2. 사용자 파기 요청 (T-180)
정보주체의 파기 요청이 로그 보관 기간보다 짧을 경우, 요청 우선. 단 **권한 감사 로그(§2-4)** 는 통계 식별자(actor_id) 로 해시화하여 보관 가능 — 이는 §2-4 로그에서 userid 를 별도 가명처리 컬럼으로 분리해야 하는 구조 변경을 요함. 별도 이슈.

### 4-3. R2 측 자동 회전
R2 라이프사이클 규칙으로 `postgres/*` 14일 자동 삭제를 설정하면 CronJob 의 `mc rm` 은 redundant. 중복 운영은 안전망이므로 **둘 다 유지**. 다만 R2 규칙 설정 후 재검토.

## 5. 이 정책이 깨지는 시나리오 (감지)

- kubectl logs 만 의존하는 현 상태에서는 **파드 재시작 = 로그 유실**. 법정 최소치에도 못 미칠 가능성. → T-042 Loki 도입 전까진 "로그 보관 = 실질 best-effort" 임을 인지.
- audit log CronJob 실패 → 로그가 무한 누적, PV 고갈. Phase 2 에 alert 포함 필수.
- R2 자동 rotation 과 CronJob `mc rm` 둘 다 실패 → 장기간 오래된 dump 누적 → 용량/비용 이슈.

감지는 T-040 Uptime Kuma / T-042 Loki alert 에 위임.

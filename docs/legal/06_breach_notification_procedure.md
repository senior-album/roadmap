# 개인정보 유출 72시간 신고 절차

**최종 수정일**: 2026-04-24 (초안)
**관련 이슈**: T-181 (roadmap#66)
**법적 근거**: 개인정보보호법 §34, §34-3 (2023 개정 반영)

> ⚠️ 법률 문서 자체가 아닌 **내부 대응 절차**. 실제 유출 시 법무 검토 병행 필수.

---

## 0. 이 문서가 답하는 것

유출 의심 상황 발견 시 **누가, 몇 시간 안에, 누구에게, 어떤 내용을** 통지해야 하는지. 법적 시한을 놓치지 않기 위한 체크리스트.

---

## 1. 법적 요구 (요약)

### 1-1. 정보주체 통지
**72시간 이내** 정보주체(당사자)에게 통지 (개인정보보호법 §34 ①). 구체적 사실 확인 전이라도 알린 사실·시점은 우선 알리고, 추가 확인된 내용은 후속 통지.

### 1-2. 규제기관 신고
- **1천 명 이상** 정보주체 정보 유출 시: **72시간 이내** 개인정보보호위원회 + 한국인터넷진흥원(KISA) 에 **신고** (§34 ③)
- **민감정보 / 고유식별정보** 포함 시: 수량 무관 신고 (§34-3)
  - 본 서비스 기준: 건강 메모(`medical_notes`), 얼굴 생체정보(embedding) 가 해당. **사실상 모든 유출이 신고 대상**.

### 1-3. 통지/신고 내용 (§34 ①, ③ 공통)
1. 유출된 **개인정보 항목**
2. 유출된 **시점과 경위**
3. 유출로 발생 가능한 **피해 최소화 방법**
4. 회사의 **대응 조치 및 구제 절차**
5. 정보주체가 도움받을 수 있는 부서, 담당자 **연락처**

---

## 2. 감지 → 최초 대응 (첫 1시간)

### 2-1. 유출 감지 경로 (이 목록에 잡히면 §2-2 로)
- Uptime Kuma / 로그 감시에서 **비정상 접근** 패턴 (대량 조회, 특이 User-Agent, 비정상 IP 대역)
- gitleaks / pip-audit / Trivy 가 **이미 배포된 이미지에 평문 secret** 검출
- 외부 제보 (보호자, 시설, 보안 연구자) 로부터 유출 가능성 통보
- 관리자 계정 탈취 / 비밀번호 재설정 요청 급증
- `photo_audit_logs` / `admin_audit_logs` 에서 권한 범위 초과 조회 흔적
- 백업(R2) 접근 키가 노출되어 third-party 접근 가능성

### 2-2. 최초 대응 (발견자)
1. **발견 시각 기록** (UTC + KST, ±1분 정확도). 이게 72시간 타이머의 기준점.
2. **슬랙/채널/직통 연락** 으로 책임자(대표/CTO) 에게 통보.
3. 발견 화면/로그 **스크린샷** 저장 (증거 보전). 원본 로그도 별도 보관.
4. 공개 발언/SNS 포스팅 **금지**. 추측성 보고도 금지.

### 2-3. 책임자 판단 (§2-1 신호가 실제 유출인지)
- 아니라고 판단 → 사유 기록하고 종결. 추후 감사 대비 로그만 남김.
- 의심 → §3 로 즉시 진입. **시한은 §2-2 의 발견 시각부터**.

---

## 3. 영향 범위 산정 (1~6시간)

### 3-1. 조사 체크리스트
- [ ] 유출 추정 **데이터 항목** (예: `residents.name`, `medical_notes`, 얼굴 embedding)
- [ ] 유출 **정보주체 수** (시설/입소자/보호자 각각)
- [ ] 유출 **경로** (DB/오브젝트/백업/로그/API 등)
- [ ] 유출 **창구의 상태**: 여전히 유효한가 / 차단 가능한가
- [ ] **언제부터** 유출 가능 상태였나 (원인 시점. 발견 시점과 다를 수 있음)
- [ ] 3rd party 가 실제로 **접근한 증거** 있는가 / 가능성만 있는가

### 3-2. 참조 로그
- `photo_audit_logs` — 사진 조회/공유
- `admin_audit_logs` — 관리자 특권 행위 (T-102 이후)
- Cloudflare 대시보드 — 이상 트래픽 패턴
- `kubectl -n senior-album logs deploy/backend --since=<t>` — API 호출 기록
- 백업 (R2) 접근 기록 — R2 대시보드

## 4. 통지 (최대 72시간 이내)

### 4-1. 시한 계산
- **시작**: 최초 발견 시각 (§2-2)
- **마감**: 발견 시각 + 72시간

3일 안에 완료해야 하는 것:
1. 정보주체 (사용자) 통지
2. 개인정보보호위원회 신고 (본 서비스는 민감정보 포함 → 무조건 대상)
3. KISA 신고 (1천 명 미만이라도 민감정보면 필요)

### 4-2. 정보주체 통지 수단
이메일 > 서비스 내 알림 > SMS 순. 이메일 주소 미보유 시 홈페이지 공지 30일 이상.

### 4-3. 규제기관 신고 창구
- 개인정보보호위원회: https://www.pipc.go.kr 및 개인정보침해 신고전화 118
- KISA 개인정보침해신고센터: https://privacy.kisa.or.kr

둘 다 온라인 신고 폼 제공. 72시간 전 내용 확정 어려우면 **"조사 중" 상태로 우선 신고** 후 추가 통지 가능 (§34 ①).

### 4-4. 통지 템플릿

```
제목: [Senior Album] 개인정보 유출 안내

[정보주체 성함]님께,

Senior Album 을 이용해주셔서 감사드립니다.
회사는 최근 아래와 같은 사실을 확인하였고, 개인정보보호법 제34조에
따라 다음 내용을 안내드립니다.

1. 유출 일시 및 경위
   - 발견 시각: YYYY-MM-DD HH:MM (KST)
   - 경위: [예: 데이터베이스 백업 파일이 외부 저장소에 접근 가능한
     상태로 YYYY-MM-DD 부터 YYYY-MM-DD 까지 노출됨]

2. 유출된 개인정보 항목
   - [예: 성함, 생년월일, 휴대폰 번호, 건강 메모]

3. 피해 최소화를 위한 조치
   - [예: 해당 저장소 접근 키 즉시 회전, 비밀번호 변경 권고]

4. 회사가 취한 대응
   - [예: 서비스 전구간 로그 조사 완료, 추가 유출 가능성 차단]

5. 문의처
   - 개인정보 보호책임자: [이름] ([이메일])
   - 문의 전화: [번호]

[회사명] 드림
```

### 4-5. 규제기관 신고 요약서

신고 폼 작성 시 미리 준비:
- 유출 일시/경위 (§3-1 체크리스트 결과)
- 정보주체 유형별 수 (시설/입소자/보호자)
- 유출 정보 항목 구체 리스트
- 원인 분석
- 취한/취할 예정 조치
- 담당자 연락처

---

## 5. 사후 조치

### 5-1. 재발 방지 (30일 이내 완료 권장)
- 원인 기반 수정 (코드/인프라/프로세스)
- 해당 공격 벡터에 대한 자동 감시 (Uptime Kuma / Loki alert)
- 관련 런북 업데이트

### 5-2. 공지 후속
- 최초 통지가 "조사 중" 상태였다면 확정 정보 후속 통지 (30일 이내)
- 서비스 내 공지 30일 이상 유지

### 5-3. 기록 보관
유출 사건 자체의 기록은 **5년 이상** 보관 (감사 대응). `docs/incidents/YYYY-MM-DD-<slug>.md` 형식으로 commit.

## 6. 사전 준비 체크리스트

이 절차가 실제로 돌아가게 하려면 **평시에** 다음 것들이 존재해야 함:

- [ ] **정보주체 연락 수단** — 유효한 이메일/SMS 주소. DB `users.email`, `users.phone` 현행성 점검 (분기 1회).
- [ ] **개인정보 보호책임자(DPO)** 지정 — 이름/연락처 공개. 현재 미지정 (roadmap#60 개인사업자 등록 후 정식화).
- [ ] **regulatory contact 샘플** — pipc / KISA 신고 폼을 한 번 "연습" 작성해두기 (실제 제출은 안 함).
- [ ] **장애 감지 수단** — Uptime Kuma (T-040), Loki alert (T-042), audit log 조회 (T-101/102). 이 중 하나라도 없으면 §2-1 감지가 "운 좋게 발견" 에 의존.
- [ ] **audit log 보관 기간** — T-182 로그 보관 정책과 일치 확인 (유출 조사 시 최소 90일치 필요).

## 현황 분석 (2026-04-22)

### 현재 구조
- `JWT_EXPIRE_MINUTES=10080` (7일) — `app/core/config.py:26`
- `JWT_REFRESH_THRESHOLD_MINUTES=1440` (1일) — 남은 시간 1일 미만이면 갱신한다는 플래그 (실제로 어디서도 쓰이지 않음)
- `/auth/refresh` 엔드포인트는 **access token을 access token으로 재발급**하는 구조 — 진짜 refresh token이 아님
- 쿠키 `access_token` httpOnly, `max_age=7일`

### 60분 축소가 단독으로 위험한 이유
refresh 토큰 없이 access TTL만 60분으로 줄이면 → 보호자가 사진 보다가 1시간마다 세션 끊김 → **UX 재앙**. 타겟 유저층이 고령 보호자(50-70대)임을 고려하면 재로그인 빈도는 치명적.

### 결정이 필요한 것 3가지

**A. Refresh 토큰 저장 위치**
- (A1) httpOnly secure 쿠키 2종 (access + refresh, 경로 분리) — 구현 단순, CSRF 주의
- (A2) access는 쿠키, refresh는 DB 테이블에 jti + user_id 저장 (rotation + revocation 가능) — 추천
- (A3) Redis에 refresh 저장 + TTL 자동 관리 — DB 부담 X, 재시작 시 전체 로그아웃 문제

**B. Refresh 토큰 수명**
- (B1) 14일 rotation (사용 시 새 토큰 발급 + 기존 invalidate) — 표준
- (B2) 30일 sliding (유저 편의, 보안 약함)
- (B3) 세션 하나당 refresh 무제한 (절대 금지)

**C. Rotation & Reuse Detection**
- 동일 refresh를 2번 이상 쓰면 계정 강제 로그아웃 → 토큰 탈취 감지
- 구현하려면 DB 저장 방식(A2) 필요

### 권장안
A2 + B1 + C (DB 저장 + 14일 rotation + reuse detection).
근거:
1. Sealed Secrets(T-050) 도입 전까진 JWT_SECRET 로테이션이 비용 — refresh를 DB에 두면 SECRET 교체 시 세션 일괄 무효화 가능
2. 고령 보호자 14일 sliding이면 재로그인 월 2회 수준 — 허용 범위

### 선행 블로커
- **T-050 (Sealed Secrets)**: refresh 서명 키를 매니페스트 평문으로 둘 수 없음
- **T-054 (bcrypt rounds=12)**: refresh 구현할 때 password 재해싱 정책과 엮임

### 선택지 확정 대기 중
담당자가 A/B/C 조합 결정해주시면 구현 PR 올리겠습니다.
단, **JWT_EXPIRE_MINUTES 60으로 축소는 refresh 구조 없이 단독 머지 금지**.

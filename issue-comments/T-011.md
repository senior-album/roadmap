## 현황 분석 (2026-04-22)

### 문제 정의
- **Presigned URL TTL**: 1시간 (`storage.py:123` `expires_in=3600` 하드코딩)
- **공유 링크 TTL**: 72시간 (`config.py:67` `SHARE_LINK_EXPIRE_HOURS=72`)
- **결과**: 공유 링크를 받은 사람이 **1시간 뒤에 열면 이미지 URL 만료** → 404 이미지

### 현재 코드 흐름 (photos.py:862-956)
```
[생성] POST /photos/{id}/share
  → share_token 발급 (72h TTL)
  → to_presigned(original_url, expires_in=3600) ← 응답에 포함된 URL은 1h만 유효

[조회] GET /photos/shared/{share_token}
  → share.expires_at 검증 (72h까지 OK)
  → to_presigned(photo.original_url) ← 매번 새로 생성 (1h 유효)
```

즉, **GET 조회 시에는 이미 매번 재발급**되고 있음. 문제는 **POST 응답의 `photo_url`이 1h 후 죽는다**는 것 — 프론트/알림톡이 이 URL을 캐시해서 쓰면 망가짐.

### 결정이 필요한 것

**A. 공유 링크 조회 방식**
- (A1) 현재 그대로 — `photo_url` 필드는 "즉시 조회용"으로 1h 유효, 재접근은 `/photos/shared/{token}` 호출해서 새 URL 받기 → 프론트/알림톡이 원본 URL을 캐시 안 하는 계약 필요
- (A2) 응답에서 `photo_url` 제거 — 항상 `share_url` (우리 서버 경유)만 제공, 브라우저가 `GET /photos/shared/{token}` 호출 → 내부에서 presigned 재발급해서 302 redirect
- (A3) presigned TTL을 72h로 올림 — MinIO는 가능하지만 S3는 일부 SigV4 조건에서 7일 상한 & TTL 길어지면 URL 공유 시 실질적으로 PII 노출 기간 연장 (보안 후퇴)

**B. Rate limit 영향**
A2를 택하면 `/photos/shared/{token}` 호출이 이미지 로드마다 발생 → 현재 30/min rate limit으로 부족 가능. 302 redirect + 캐시 헤더(max-age=3500)로 완화 가능.

### 권장안
**A2 (항상 서버 경유 + 302 redirect)** 채택.
근거:
1. 응답 JSON에 만료 다른 두 TTL이 공존하면 클라이언트가 실수하기 좋음 — 계약으로 강제 불가
2. A3는 I-04 위협(생체사진 URL 확산) 악화
3. 302 + Cache-Control로 브라우저가 URL을 한 번만 fetch 후 이미지만 CDN/브라우저 캐시에 남김 → rate limit 부담 없음

### 구현 체크리스트 (A2 확정 시)
- [ ] POST `/photos/{id}/share` 응답에서 `photo_url`, `thumbnail_url` 필드 제거 — `share_url` + `thumbnail_proxy_url`만 반환
- [ ] GET `/photos/shared/{token}`을 JSON 응답 + `GET /photos/shared/{token}/image`, `/thumbnail` 엔드포인트로 분리
- [ ] 이미지 엔드포인트는 presigned URL 재발급 후 302 redirect + `Cache-Control: private, max-age=3500`
- [ ] 프론트 `SharedPhotoPage.tsx` — `photo_url` 참조 제거, 새 이미지 엔드포인트 사용
- [ ] 알림톡 템플릿 — 첨부 이미지 필드에 `share_url` 경유하도록 확정
